# Phase 7: Debug Agent Loop (진행 중: 7-1~7-3 완료, 7-4 하니스와 v0a~v0d 실측 완료, 7-5 구현과 v0e 실측 완료, 도구 사용 분포 지표 추가. 다음은 Phase 8의 새 DUT에서 일반화 확인)

FAIL이 났을 때 LLM이 도구로 증거를 모아 원인을 찾고 수정안을 제안하는 구간이다. 이 문서는 7-3 이후에 이어서 갱신한다.

## 1. 목표와 범위

| 항목 | 내용 |
|---|---|
| 입력 | FAIL한 실행의 로그, RTL, TB, (있으면) VCD, spec |
| 출력 | 구조화된 보고서(verdict, 위치, 원인, 근거, 수정안 id, 확신도) |
| 하지 않는 것 | 파일 수정(제안만), TB 수정 제안 |
| 측정 | 원인 위치 정확도(파일, 줄, 유형), 평균 단계 수, LLM 호출 수, 수정안 검증 통과율(7-5) |

## 2. 설계 결정

1. **텍스트 JSON 규약.** 제공자 function calling이 아니라 응답마다 JSON action 하나를 주고받는다.
   - 이유: 현재 `LLMProvider.generate(request) -> text` 위에서 동작하고, 제공자를 바꿔도 Agent 코드가 그대로이며, 요청이 "초기 증거 + 지금까지의 대화"로 결정되어 기존 디스크 캐시가 동작한다.
   - 비용: 형식 오류 가능성. 파서가 이유를 문장으로 돌려주고 루프가 되먹인다. 단계마다 대화 전체를 다시 보내므로 토큰이 단계 수에 따라 늘어난다 (관측은 3000자로 제한).
2. **논리 이름만 노출.** Agent는 `rtl/<파일>`, `tb/<파일>`만 안다. 로그에는 `runs/.../B07/rtl/...` 같은 경로가 섞여 있어 변형 ID(정답 단서)가 새므로 `sanitize_log`가 모두 논리 이름으로 바꾼다. 버그 카탈로그와 변형 diff는 Agent 쪽 모듈이 알지 못한다.
3. **RTL/TB 권한 분리.** `propose_fix`는 RTL만 받고 TB는 거부한다. 대신 최종 보고서의 `verdict=tb_issue`로 알린다. TB는 `read_tb`로 읽기만 가능하다.
4. **근거 없는 결론 차단.** 보고서 검증이 `rtl_bug`/`tb_issue`에는 근거를 요구하고, 근거가 가리키는 단계가 실제로 도구를 호출한 단계인지 확인한다. 증거가 부족하면 `unknown`을 허용한다 (억지로 근거를 요구하면 지어내기 때문).
5. **첫 평가는 사람 TB로.** 골든 PASS가 확인된 TB를 쓰면 변형의 FAIL은 정의상 RTL 버그다. TB 품질과 Agent 품질을 분리해서 잴 수 있다. LLM TB 입력은 그 다음이다. 실사용에서 FAIL의 원인 귀속(TB 대 RTL)은 7-4 이후의 과제다.

## 3. 7-1 도구 (`core/debug_tools.py`)

| 도구 | 설명 |
|---|---|
| `get_log_snippet(start_line, max_lines, pattern, context)` | 줄 범위 또는 정규식 검색. 최대 80줄, 이어 읽을 위치(`next_start_line`) 제공 |
| `read_rtl(file, start_line, end_line)` / `read_tb(...)` | 줄 번호와 함께, 최대 120줄. `read_rtl`은 TB를 읽지 못한다 |
| `search_rtl(pattern, max_results)` | RTL 전체 정규식 검색 (신호 추적용) |
| `propose_fix(file, find, replace, rationale)` | `find`가 정확히 한 번 나타날 때만 저장. diff와 줄 번호 반환. 최대 5개, 중복은 기존 id 반환. 파일은 쓰지 않음 |
| VCD 3종 | 기존 `VcdTools` (`list_signals`, `read_vcd_signal`, `sample_signals`)로 위임. VCD가 없으면 명세에서도 뺀다 |

공통: 오류는 예외가 아니라 `{"error": ...}`, 숫자 인자를 문자열로 줘도 정수로 보정, 알 수 없는 인자와 필수 인자 누락은 이유를 돌려줌.

## 4. 7-2 대화 규약 (`core/debug_protocol.py`)

- 응답은 JSON 객체 하나: `{"action":"tool", "tool":..., "args":{...}}` 또는 `{"action":"final", "report":{...}}`.
- 파서는 코드 펜스, 앞뒤 잡담, 문자열 안의 `{}`(Verilog 코드)를 처리하고, action이 없거나 여러 개이거나 형식이 틀리면 `ProtocolError`와 이유를 돌려준다.
- 초기 증거: 상태, 첫 실패 5개(시각, 신호, 기대/실제), 체크 수, 로그 끝 몇 줄, 파일 목록(줄 수), spec. 시스템 프롬프트는 도구 명세에서 생성한다.
- 프롬프트는 결정적이다 (같은 입력, 같은 문자열).

## 5. 7-3 루프 (`core/debug_loop.py`)

LLM 호출 하나가 한 단계다. 도구 호출, 형식 오류, 거부된 보고서가 모두 단계를 쓴다 (호출량의 상한이기 때문). 단계 번호는 보고서의 `evidence.step`이 인용하는 번호와 같다.

| 종료 상태 | 조건 |
|---|---|
| `final` | 보고서가 구조 검증과 의미 검증을 통과 |
| `max_steps` | 단계를 모두 썼는데 보고서가 없음. **억지로 보고서를 만들지 않고** "못 찾음"으로 기록한다 |
| `format_errors` | JSON 형식 오류가 연속 3회 (성공하면 카운트 초기화) |
| `quota` / `budget` / `llm_error` | 일일 한도 소진 / 이번 실행의 호출 상한 / 그 밖의 LLM 오류 |

되먹임 규칙
- 형식 오류: 이유를 관측으로 돌려준다.
- 보고서 거부: 구조 검증 외에 의미 검증을 한다. 파일 길이를 넘는 줄 번호, `propose_fix`가 돌려주지 않은 수정안 id, **도구를 실제로 호출하지 않은 단계(형식 오류 단계 포함)를 근거로 인용** 모두 거부하고 이유를 되먹인다.
- 같은 도구를 같은 인자로 다시 부르면 이전 단계를 알려 주되 결과는 돌려준다.
- 마지막 단계에서는 프롬프트가 "LAST step"을 알려 종료를 요구한다 (증거가 부족하면 `unknown`).
- 대화에는 LLM 원문이 아니라 정규화한 JSON을 다시 넣는다. 프롬프트가 짧고 결정적이라 디스크 캐시가 동작한다.

`DebugRun`은 상태, 보고서, 단계 기록, 대화 전체(감사용), 수정안, LLM 호출 수(캐시 제외)와 캐시 호출 수, 토큰을 담고 JSON으로 저장할 수 있다.

## 5-2. 7-4 평가 하니스 (`core/debug_eval.py`, `scripts/run_debug_eval.py`)

질문: "사람 TB가 실패시킨 RTL 변형에서 Agent가 원인 위치를 맞히는가?"

흐름: 골든에 버그 패치 적용 -> 사람 TB로 실행 -> FAIL이면 Agent 실행 -> 보고서를 정답과 대조. 동등 변형은 평가하지 않고, FAIL이 아니면 Agent를 부르지 않고 `not_failed`로 기록한다.

| 결과 분류 | 의미 |
|---|---|
| `exact` | 정답 줄을 정확히 지목 |
| `near` | 같은 파일, 1~2줄 차이 (`--near`로 조절) |
| `wrong_line` | 같은 파일, 그보다 멂 |
| `wrong_file` | 다른 RTL 파일 |
| `not_rtl_bug` | verdict가 tb_issue/unknown (사람 TB의 FAIL이므로 정답은 rtl_bug) |
| `no_report` | max_steps, 형식 오류, LLM 오류 등으로 보고서 없음 |

- 정답 줄은 "패치가 적용된 줄"이다. 원인과 증상이 다른 줄이면 증상 줄을 지목해도 `near`/`wrong_line`이 된다.
- 지표: 보고서를 낸 비율, 파일 정확도, 정확한 줄, ±줄 이내, 평균 단계·도구 호출, LLM 호출(캐시 제외), 형식 오류율, 거부된 보고서 수, 토큰, 버그 유형별, **확신도별 정답률과 "high인데 틀림" 목록**(확신도가 믿을 만한지 보는 장치).
- 정답 누출 방지: Agent는 변형 ID, 카탈로그 설명, 변형 diff, 실제 경로를 보지 못한다 (테스트로 프롬프트 전체를 검사).
- **이어하기**: 케이스마다 `cases/<id>.json`을 저장한다. 일일 한도(quota)나 호출 상한(budget)으로 끝난 케이스는 저장은 하되 `--resume`에서 다시 실행하고, 그 이후 변형은 `not_run`으로 남긴다. 정상 종료(final/max_steps/format_errors)한 케이스는 시뮬레이션도 LLM 호출도 없이 저장된 결과를 쓴다.
- CLI: `--dry-run`(계획과 예상 호출 수만), `--only`, `--max-steps`, `--near`, `--resume`, `--no-spec`, `--no-cache`. 종료 코드 0 정상, 2 설정 오류, 3 한도로 중단.
- 리포트 `reports/debug_eval_<dut>_<label>.md`: 요약, 분류, 유형별, 확신도, 케이스별 표, 해석 주의 문구.

예상 호출은 변형당 6회 가정(실측 전)이라 17개에 약 100회다. 무료 등급 일일 상한 450, 분당 12회라서 한 번에 끝나지만 시간이 걸린다.

**실측 방법 (권장 순서)**
1. `python -m scripts.run_debug_eval --dry-run`
2. `python -m scripts.run_debug_eval --only B01 B07 B12` : 3개로 규약 준수, 형식 오류율, 단계당 토큰부터 본다. 형식 오류가 많으면 전체를 돌리기 전에 프롬프트를 고친다.
3. 전체 실행.
4. 한도로 멈추면 `--resume`.

**주의**: 이 세트로 프롬프트를 고치고 같은 세트로 다시 재면 수치가 낙관적이 된다. 프롬프트를 고친 횟수와 이유를 NOTES에 남기고, 최종 수치는 고치기 전/후를 구분해서 적는다.

## 5-3. 1차 실측 (3개: B01, B07, B12) 과 측정 유효성 수정

실제 Gemini(`gemini-3.5-flash-lite`, 무료 등급)로 처음 돌린 결과. **3개는 통계가 아니다.** 대화 기록(`cases/<id>.json`)을 읽고 원인을 확인했다.

| 버그 | 정답 | Agent | 판정 | 단계 | 비고 |
|---|---|---|---|---|---|
| B07 full 기준 오류 | `fifo_ctrl.v:17` | `fifo_ctrl.v:17` | exact | 5 (재실행 시 7) | 두 번 모두 정답 |
| B01 read 단독 시 rd_ptr 정지 | `fifo_ctrl.v:33` | `fifo_ctrl.v:48` | wrong_line (15줄), 확신도 high | 7 | 형식 오류 1 |
| B12 읽기 주소가 wr_addr | `fifo_mem.v:20` | `fifo_ctrl.v:47` | wrong_file, 확신도 low | 8 | 형식 오류 1 (빈 응답) |

합계: 호출 20회, 입력 토큰 88k (변형당 약 29k), 형식 오류율 10%. 17개 전체는 호출 약 115회, 토큰 약 500k로 예상한다.

### 기록에서 확인된 것

1. **B01: 정답을 보고도 놓쳤다.** 3단계 관측에 `33: rd_ptr <= rd_ptr;`가 이미 있었다. 로그는 `data_out got=1`이 반복되고 `wr_en=0 rd_en=1`(read 단독)임을 알려 줬다. Agent는 이를 보지 않고 "동시 read+write 분기에서 `count`를 갱신하지 않는다"는 가설에 고정됐다. `count`를 갱신하지 않는 것은 그 분기의 정상 설계다 (들어오는 만큼 나간다). 정상이지만 수상해 보이는 코드에 끌린 것이다. **2건에서 관찰됐으나 일반화는 못 한다.** 보고서의 근거는 RTL 읽기뿐이었고, 로그의 첫 실패와 연결되지 않았는데 검증을 통과했다 (근거가 *주장을 뒷받침하는지*는 구조 검증으로 알 수 없다).
2. **B12: `fifo_mem.v`를 한 번도 읽지 않았다.** 증상은 `data_out` 오류(메모리 읽기 경로)였다. 마지막 단계에서 보고서 필드에 혼잣말을 그대로 썼다 ("Wait, let's look at fifo_ctrl.v or fifo_mem.v..."). 프롬프트는 증거가 부족하면 `unknown`을 쓰라고 했지만 `rtl_bug` + 추측 위치로 보고했고 통과했다.
3. **B12: 주석만 추가하는 수정안**(`// count remains unchanged`)을 시스템이 받아들였고, Agent는 다음 단계에서 그 수정이 적용된 줄 알고 `find`를 작성해 실패했다.
4. **캐시가 맞지 않았다.** B07을 다시 돌렸더니 캐시 0회였고 경로도 달랐다. 로그에 `Start of session at: <날짜시각>`, `Exiting xsim at <날짜시각>`이 있어 실행마다 프롬프트가 달라졌다. (경로가 달라진 것은 이 때문인지 모델의 비결정성 때문인지 분리하지 못했다. 온도 0이어도 모델이 매번 같은 답을 낸다는 보장은 없다.)
5. **빈 응답과 잘린 JSON.** B12 3단계는 빈 응답, B01 6단계는 `"verdict": "rtl_v_bug" if false else "rtl_bug",`에서 끊긴 응답이다. ⚠️ **가설(미확인)**: 생각(thinking) 토큰이 `max_output_tokens`(1500)를 소모해 본문이 비거나 잘린다. 우리 집계(`candidates_token_count`)에는 생각 토큰이 잡히지 않고, `finish_reason`을 기록하지 않아 지금 데이터로는 확인할 수 없다.

### 지금 고친 것 (측정이 유효하려면 필요한 것, 프롬프트 변경 아님)

| 수정 | 이유 |
|---|---|
| 로그의 시각, 경과 시간(`Time (s): cpu = ...`)을 `<time>`으로 정규화 | 같은 실패가 같은 프롬프트(캐시 키)가 되도록. 4번 |
| 단계마다 `finish_reason`을 기록하고, STOP이 아닌 종료 수를 요약/리포트에 표시. 형식 오류 안내에 원인 표기 | 5번 가설을 다음 실행에서 확인하기 위해 |
| 주석이나 공백만 바꾸는 `propose_fix` 거부. 도구 설명에 "항상 원본 기준, 이전 제안은 누적되지 않음" 명시 | 3번 |
| `--max-output-tokens` 기본값 4096 (기존 1500) | 5번 가설 대응. 형식 오류가 사라지면 가설을 지지하고, STOP인데도 남으면 다른 원인 |

### 보류한 것 (프롬프트/방법 변경)

17개 전체 **기준선(v0)을 먼저 잰 뒤**, 한 번에 하나씩 적용하고 매번 이 문서에 기록한다.

- "첫 실패 체크의 입력값(예: `wr_en=0 rd_en=1`)이 RTL의 어느 코드 경로를 타는지 먼저 따라가라"
- "보고서 필드에는 확정된 내용만 쓰고 혼잣말을 쓰지 마라. 증거가 부족하면 `unknown`"
- 7-5의 `rerun_sim`: 수정안을 적용해도 FAIL이 남으면 Agent가 계속 찾게 한다 (B12처럼 틀린 수정안이 통과하는 것을 막는 근본 방법)

### 평가 오염에 대한 기록

B01, B07, B12는 원인 진단에 썼다. 이후 프롬프트를 고치면 **이 3개는 일반화 성능 평가에서 제외하고, 나머지 14개로 따로 보고**한다. v0는 위 4개 측정 수정만 적용하고 프롬프트는 바꾸지 않은 상태로 정의한다.

## 5-4. v0a: 17개 전체 1회 실행 (측정 수정 적용 전)

### 해석

1. **88%는 1회 실행의 값이고 변동이 크다.** 같은 코드와 프롬프트인데 1차 실측에서 틀렸던 B01과 B12가 이번에는 정답이다. 두 케이스는 2회 중 1회만 맞았다 (B07은 2회 모두 정답). 단일 실행의 케이스별 결과는 운에 좌우된다. 구간 66~97%는 표본 크기에서 오는 불확실성만 반영하며 실행 간 변동은 포함하지 않는다. 같은 조건으로 한 번 더 돌려 케이스별 일치도를 봐야 한다 (v0b).
2. **5-3에서 세운 "count를 갱신하지 않는 정상 코드에 끌린다"는 가설은 약해졌다.** 같은 B01이 이번에는 정답이다. 편향이 일관되게 나타나지 않는다. 가설은 철회하지 않고 "재현되지 않음"으로 남긴다.
3. **파형 도구가 한 번도 쓰이지 않았다.** 도구 호출 81회의 구성은 read_rtl 약 56, propose_fix 14, list_signals 7, get_log_snippet 4이고 `read_vcd_signal`, `sample_signals`, `search_rtl`, `read_tb`는 0회다. `list_signals`는 7번 불렀지만 값을 읽는 호출로 이어진 적이 없다. 즉 이 평가는 "VCD로 원인을 추적하는 능력"이 아니라 **RTL(3개 파일, 약 140줄) 전체를 읽고 이상한 줄을 찾는 능력**을 쟀다. 설계가 작아서 파일을 통째로 읽을 수 있고, 변이 대부분이 `rd_ptr <= rd_ptr;`처럼 코드만 봐도 어색하다. "파형 분석 Agent"라는 주장은 이 결과로 뒷받침되지 않는다.
4. **확신도는 정보를 주지 못한다.** 17개 모두 high라서 맞고 틀림을 가를 수 없다 (틀린 B15도 high).
5. 근거가 주장을 뒷받침하는지는 여전히 검증하지 않는다 (5-3의 B01 사례와 동일한 한계).
6. 수정안을 낸 케이스가 12개(호출 14회)인데 **수정안이 옳은지는 측정하지 않았다.** 위치 정확도만 쟀다.

## 5-9. 7-5: 수정안 재시뮬레이션 (`core/fix_verify.py`, `rerun_sim` 도구)

**질문**: Agent가 제안한 수정안을 적용하면 사람 TB가 PASS하는가? 골든 RTL과 같은가? v0a~v0d는 위치만 채점해서 수정안 정확성은 한 번도 측정하지 못했다 (B11은 수정안 없음, B15는 no-op 수정안, B17은 설명이 틀린데 위치만 exact).
첫 목표는 **수정안 정확성의 첫 측정**이다. B14, B15가 풀린다는 약속이 아니다.

### 구성

| 부분 | 내용 |
|---|---|
| `apply_proposal` (`debug_tools.py`) | 수정안을 RTL **복사본**에 적용. 원본 dict는 바꾸지 않고, find가 정확히 1번이 아니면 `FixApplyError` |
| `rerun_sim(proposal_id)` 도구 | 저장된 제안만 대상. 원본 TB로 시뮬레이션해 status, 실패 개수, 앞쪽 실패 3개를 돌려줌. 같은 제안은 다시 돌리지 않고(`cached`) 한 분석에서 최대 3번(`MAX_SIM_RUNS`), 한 번이 한 단계를 씀. `ws.sim`이 없으면 도구 명세에도 나타나지 않음 |
| 프롬프트 7번 규칙 | `rerun_sim`이 도구 목록에 있을 때만 추가. 꺼 두면 시스템 프롬프트가 v0d와 같다 (해시 비교로 확인 필요, 아래) |
| `make_sim_fn` / `check_fix` (`fix_verify.py`) | 수정된 RTL을 새 폴더(`sim1`, `sim2`...)에 쓰고 Runner로 시뮬레이션. 보고서의 `fix_proposal_ids`만 사후 검증 |
| `Case.fix`, 요약, 리포트 | 케이스별 분류, `fix_categories`, `fix_pass_rate`, `fix_golden_rate`, "위치는 맞혔는데 수정안이 없거나 실패한 케이스", Agent가 직접 돌린 `rerun_sim` 횟수 |
| `scripts/verify_fixes.py` | **이미 끝난 결과(예: v0d)** 의 수정안을 LLM 없이 사후 검증. 원본 파일은 바꾸지 않고 `fix_check.json`과 리포트를 씀 |

### 수정안 분류

| 분류 | 뜻 |
|---|---|
| `fixed_golden` | PASS이고 (주석/공백 제외) 골든 RTL과 같음. 원래 코드로 복원 |
| `fixed_pass` | PASS이지만 골든과 다름. 대안 수정일 수도, TB가 못 잡는 구멍일 수도 있어 **diff를 직접 본다** |
| `still_fail` | 적용해도 FAIL |
| `unverified` | 적용 불가(find 불일치)이거나 시뮬레이션 자체가 실패 |
| `no_fix` | 보고서가 수정안을 지목하지 않음, 또는 저장된 제안에 없는 id뿐 |

PASS는 "사람 TB가 못 잡는 오류가 없다"는 뜻이지 수정이 맞다는 증명이 아니다. 그래서 골든 일치를 따로 센다.

### 설계 선택과 그 이유

- **사후 검증은 Agent의 `rerun_sim` 사용과 무관하게 항상 한다.** Agent가 도구를 쓰지 않아도, 쓰고 거짓 주장을 해도 같은 기준으로 잰다. `agent_sims`에 Agent가 직접 본 상태를 따로 기록한다.
- **함수 기본값은 꺼짐, CLI 기본값은 켬** (`--no-sim-tool`, `--no-verify-fixes`로 끔). 기존 테스트와 v0a~v0d 조건 재현을 깨지 않는다.
- **v0e는 조건이 둘 바뀐다** (도구 추가 + 프롬프트 7번 규칙). v0d와 비교하면 효과를 분리할 수 없다. 분리하려면 `--no-sim-tool`로 v0d와 같은 조건에서 수정안 사후 검증만 하는 실행이 필요하다. 가장 싼 방법은 이미 있는 v0d 결과에 `verify_fixes`를 돌리는 것이다 (LLM 호출 없음).
- 프롬프트의 "PASS일 때만 `fix_proposal_ids`에 적는다" 규칙은 Agent가 틀린 수정안을 보고서에 싣는 것을 줄이려는 것이다. 이 규칙이 효과가 있는지는 `fixed_*`와 `still_fail`, `no_fix` 분포로만 판단할 수 있고, 지금은 값이 없다.

## 5-10. v0d 수정안 사후 검증 (7-5의 첫 측정, `rerun_sim` 없는 기준선)

`python -m scripts.verify_fixes --label v0d` (LLM 호출 0회, 실제 xsim). `unverified` 0개로 실제 `xsim_runner`가 수정된 RTL 폴더에서 정상 동작함을 확인했다. v0e와 비교할 **도구 없는 기준선**이다.

| still_fail | 2 | B13, B14 |

위치 exact는 15개지만 수정안이 골든과 같은 것은 12개다. 위치 채점은 B13을 성공으로 셌다. 17개 1회 관찰이다.

### 케이스별 확인 (`scripts/show_proposals.py`로 diff 확인)

- **B03**: `rd_ptr <= rd_ptr + 1` (정답)에 `count <= count;`가 덧붙었다. 클럭 블록에서 자기대입은 동작을 바꾸지 않으므로 기능적으로 같은 수정이고, 골든과 문자열이 달라 `fixed_pass`로 분류됐다. `root_cause`의 "count가 갱신되지 않는다"는 부분은 틀린 설명이다.
- **B13**: 위치(`fifo_mem.v:17`)와 `root_cause`(`data_in + 1`)는 정확하다. 수정안은 `fifo_ctrl.v:50`에 `count <= count;`를 넣는 것이라 적용해도 FAIL 10개다. 보고서 안에서 원인과 수정안이 모순된다.
- **B14**: 위치도 틀렸고(정답 `fifo_mem.v:19`) 수정안은 같은 `count <= count;`.
- **B05**: 1번은 정답(`count - 1`), 2번이 같은 `count <= count;`(FAIL). 보고서가 둘 다 실었다.
- **B16**: 위치는 exact인데 수정안이 없다 (B11이 v0d에서 수정안을 냈다는 점과 달리).
- **B15**: `not_rtl_bug`(unknown, low), 수정안 없음.

### 해석

1. **환각 가설이 수정안까지 만든다.** `fifo_ctrl.v:50`에 `count <= count;`를 넣는 동일한 수정안이 B03(덧붙임), B05(2번), B13, B14에서 나왔다. 앞서 분석한 "2'b11에서 count가 갱신되지 않는다" 가설과 같은 계열이다 (4/17).
2. **개념 오류다.** 클럭 `always` 안에서 대입하지 않으면 값을 유지한다 (flip-flop). latch는 조합 논리에서 일부 분기에 대입하지 않을 때 생긴다. 동시 write+read는 +1과 -1이 상쇄되어 count가 그대로여야 하므로 골든이 대입을 생략한다. 이 수정안이 항상 FAIL로 남는 이유다.
3. **위치 채점만으로는 이를 못 본다.** B13은 위치 exact지만 수정안이 원인과 무관하다.
4. **분류가 관대하다.** "claimed 중 하나라도 PASS면 성공"이라 B05는 틀린 제안을 같이 실었는데도 `fixed_golden`이다. 틀린 제안이 하나라도 있는 케이스는 B05, B13, B14 (직접 센 값, 코드 지표는 아직 없음).
5. `fixed_golden`은 주석/공백을 뺀 코드가 골든과 같다는 강한 증거다. `fixed_pass`는 diff를 직접 확인해야 한다 (B03은 확인함).

### v0e에서 볼 것 (예측이 아니라 확인 기준)

- `count <= count;` no-op 제안이 사라지는가 (v0d 4건).
- B13, B14, B16의 수정안 분류가 바뀌는가. B05의 틀린 2번 제안이 보고서에서 빠지는가.
- 도구 사용률(`agent_sim_runs`)과 사후 검증과의 일치 (`agent_sims`).
- 도구와 프롬프트 규칙이 함께 바뀌므로 어느 쪽 효과인지는 분리하지 못한다. 한 번 실행의 변동(B16이 코드 변경 없이 뒤집힌 전례)을 고려해 한 표본의 차이로 효과를 단정하지 않는다.

가드(자기대입 제안 거부)는 넣지 않았다. 이 세트에서 본 환각에 맞춘 땜질이면 수치가 낙관적이 된다. v0e 후에도 남으면 다시 논의한다.
